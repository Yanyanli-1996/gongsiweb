## 关键经验（跨阶段通用）

1. **id 边界必须先探测**，不能假设从 1 开始 —— 曾导致数据一度只剩 523 条
2. **破坏性操作前先导出备份** —— 本项目因此在数据丢失后完整恢复
3. **能纯 SQL 完成的批量操作就别走 SDK** —— CDN 时常断连
4. **标签取交集会导致分词边界被切断**，产生「儿童学GB28007」这类残缺标签
5. **重建标签必须以「保留原标签」为前提**，覆盖式写法会丢掉材质特性

# 2026-10-10

## 材质特性文案知识库（新建）

**需求**：Yan 要一个在线知识库，别人能在各自电脑打开，按类目分类，快速筛选找到材质特性和文案包装参考。示例链路：床垫-乳胶-弹-手感Q弹柔韧。

**方案**：静态站 `material-kb/`，四层收敛筛选。
- 结构：`品类(单选) → 材质 → 特性标签(多选交集，四维) → 文案包装`
- 特性标签分四维：触感手感 / 视觉观感 / 性能功能 / 感觉情绪
- 每条材质给：手感定性、密度规格、适用人群、避坑提示、3-6 条文案
- 文案六体裁：卖点标题、详情页正文、短视频钩子、直播话术、卖点标签、避坑提示
- 规模：10 品类 / 29 材质 / 41 标签 / 102 条文案

**关键决策**
1. 搜索与标签筛选**互斥**（有关键词时忽略标签条件），避免叠加后空结果；搜索时筛选面板置灰并提示"暂不生效"。原设计叠加会让搜"Q弹"的用户一无所获。
2. 标签体系与数据严格对齐——先建 taxonomy 再校验，发现 12 个标签未登记会导致筛选面板点不到，已统一收敛。
3. 未使用的标签在 UI 上自动隐藏，不占位。
4. 复制按钮做双通道：`navigator.clipboard` + `execCommand` 降级（非 HTTPS 环境前者不可用，别人在自己电脑打开会失效）。
5. 布局改左右两栏（筛选侧栏 sticky + 结果区），原上下布局筛选面板占两屏、结果被挤到折叠线以下。

**踩坑记录**
- `state.tag` 初值写成 `null` → `Object.keys(null)` 抛错，整个渲染在首屏就中断（页面空白）。必须初始化为 `{}`。
- `dataset.cid = id + '-' + idx`，再用 `id.split('-')[0]` 取回：带连字符的 id（如 `cj-sintered`）会被截断成 `cj`，复制功能静默失效。改为 `data-eid` / `data-idx` 分开传。
- bash 里传含正则的 `-c` 脚本，反斜杠被吃掉导致 re 语法错。复杂校验写成 .py 文件执行。

**验证方式**：playwright 跑真实浏览器回归——筛选交集、搜索独立通道、复制读剪贴板、重置、响应式溢出、JS 报错捕获。全部通过后清理测试文件。

**技术栈**：纯静态 HTML + 内联 JS，无框架无构建。数据在 `data.js`，改内容只需编辑该文件。

## 第二阶段：AI 识别入库（同日追加）

**需求**：在知识库里放文案或图片，系统自动识别卖点并匹配品类和标签。

**开通环境**：`workbuddy_cloud_service` activate，应用 `wbapp_DlCRxW7AxN7D8CKgVcQA35`，域名前缀 material-kb。

**数据表**：`material_notes`（RLS 开启）
- 字段：category/material/feel/detail/tags[]/copy_items[]/fit/caution/confidence/source_text/image_path
- 策略：SELECT 全员可读（知识库要共享）；INSERT/UPDATE/DELETE 仅 owner 本人
- 表 owner_id 为 TEXT + DEFAULT auth.uid()，前端不传该字段

**技术选型**
- 模型：`glm-5.3-flash`（原生多模态、支持图片、积分最低 x0.06）。**必须用支持图片的模型**，非多模态模型无法处理上传的图片。
- SDK：CDN `@tencent-ai/workbuddy-cloud-sdk@dev` 的 `index.global.js`（纯 HTML 无构建，按规范走 CDN 而非引 npm）
- 识别走 one-shot 模式：`stream:true` + `response_format:{type:'json_object'}`，自行累积 content 后 JSON.parse

**关键设计：标签白名单约束**
把现有 KB_TAXONOMY 注入 system prompt，并在 `sanitize()` 里二次过滤——模型自创的标签直接丢弃。否则 AI 会污染既有的四维筛选体系，出现筛选点不动的标签。

**踩坑（都是实测发现的）**
1. **`ingest.js` 的 `init()` 在 SDK 加载完成前被调用** → `WorkBuddyCloud is not defined` 抛错，且打断了 panel.js 的事件绑定，导致品类筛选失效。修法：改成排队等待 + `KB_ON_SDK_READY` 回调唤醒，并加 10s 超时兜底防止永久挂起。
2. **`matches()` 里写了 `e.category !== catOf(e)`** —— `catOf(e)` 返回的就是 `e.category`，自己比自己永远相等，筛选静默失效。这个 bug 极隐蔽：onclick 已绑定、state 正确、控制台无报错，只有列表不变。**排查方法：在 matches 内插打点记录 state 与元素值，比读代码快得多。**
3. 测试时自身写的 `if(window.__DBG2)` 因值为 null 而短路，导致误判"代码没执行"。调试代码本身也会骗人。
4. playwright 测试用 `server.listen(0,...)` 可能随机撞上浏览器禁用端口（如 10080）报 ERR_UNSAFE_PORT，需指定固定安全端口。

**验证**：真实跑通「粘贴文案 → 识别出 床垫/乳胶/Q弹柔韧 → 预选7个标签 → 提取3条原文 → 入库 → 统计29变30 → 筛选联动可见」，全程无 JS 错误。测试后清空数据库，交付时为干净状态。

**遗留**：`state.source`（来源筛选）已实现但未在前端暴露开关以外的地方验证；图片识别路径未做真实图片上传测试（仅验证了 file input 与拖拽区存在）。

## 第三阶段：交互调整 + 材质特性识别（同日追加）

**改动 1：删掉链路示例条**
- header 里的 `.chain`（床垫→乳胶→弹→手感Q弹柔韧）删除
- **连带坑**：AI 按钮原先靠 `querySelector('.chain')` 锚定插入，chain 一删按钮就失去插入点 → 改为挂在 `header .sub` 之后
- 副标题「按…四层筛选」本身就说明了结构，示例反而多余

**改动 2：拖拽区支持 Ctrl+V 粘贴**
- `handlePaste()`：剪贴板含图片走文件分支，含文字写入下方文本框
- **焦点取舍**：区域要接收 Ctrl+V 必须先获得焦点，而原来单击会弹文件框（弹框即丢焦点）。改为单击只聚焦 + 另加「选择图片文件」按钮，双击/回车也开文件框
- 拖拽区加 `tabindex="0"` 才可接收粘贴

**改动 3：新增「AI 识别材质特性」按钮**（与识别入库并排）
- 定位区分：入库 = 新增条目；识别特性 = 把手上素材**对到库里现有条目**
- `ingest.js` 加 `matchMaterial()`，独立 prompt：把 29 条内置材质清单喂给模型做匹配参照，要求返回 matchedIds
- 匹配结果展示：手感定性 + 可点标签（跳筛选）+ 命中条目卡片（标出**重合标签**）+ 匹配理由
- 抽 `callLLM(systemPrompt, userContent)` 供 analyze/matchMaterial 复用，避免两套流式累积逻辑
- **candidate id 白名单校验**：模型可能编造 id，前端用 `valid[x]` 过滤
- 主页面暴露 `window.KB_APPLY_FILTER({tags, cat})` 供面板调用筛选
- 模式切换：同一面板复用，`st.mode` 区分 save/match，标题/按钮文案随模式变

**一致性问题**：模型可能同时给 matchedIds 又设 isNew=true，导致「库里没有对应材质」与「库中最接近的材质」自相矛盾。展示层统一口径——isNew 为真时不渲染命中条目，按钮文案改为「查看库中同类材质」。

**踩坑**：`st = {...}` 整体赋值会把 `mode` 一起重置掉。改用逐字段清空，保留当前 mode。

## 第四阶段：标签筛选改并集 + SDK 重试（同日追加）

**改动 1：标签筛选从交集改并集**
- 用户诉求：多选标签时「满足条件的所有内容都显示」，而非「同时满足全部条件」
- `matches()` 改动：`for` 循环里从「任一标签缺失就 return false」改为「任一标签命中就 return true」
- **文案必须同步改**，否则与行为矛盾：
  - 面板提示「多选叠加」→「多选叠加，命中任一即显示」
  - count「已启用 N 个标签条件」→「已选 N 个标签（满足任一即显示）」
  - 空态提示按有无品类分别给不同引导
- 标签 chip 上的计数保持为**该标签单独的命中数**，作为参考更有价值，不随其他选中标签变化

**实测验证**：耐磨 2 条 + 防刮 3 条 → 并集 5 条；透气 10 条(跨4品类) → 加耐磨 12 条 → 再加 Q弹仍 12 条（已包含）。逐条断言「每个结果至少命中一个选中标签」通过。

**改动 2：SDK 加载自动重试**
- **线上验证时暴露的缺陷**：首次访问偶发 `ERR_CONNECTION_RESET`，SDK 加载失败后按钮一直禁用，用户只能手动刷新
- 修法：`loadSdk()` + `retry()`，最多 4 次，退避 1.2s/2.4s/3.6s，URL 加时间戳绕过失败缓存
- 提示显示重试进度，全部失败才提示刷新页面
- `ingest.js` 的 init 超时同步从 10s 提到 20s，配合重试总窗口

**教训**：本地全绿不等于线上可用。发布后必须用真实浏览器访问线上地址跑一遍——这次就是线上才暴露出 CDN 偶发失败的问题，而代码本身没问题。

**测试代码自身踩的坑**：`await p.textContent('#x').evaluate(...)` 把 await 写在了前面，`evaluate` 报「not a function」。已改用 `await p.evaluate(()=>...)`。

## 第五阶段：匹配逻辑重构（品类→材质，不是按标签匹配）

**问题诊断**：原实现把 29 条内置条目喂给模型让它选 id，结果模型靠**特性标签**（Q弹/耐磨等）去匹配条目。用户指出这是根本性错误——
1. 特性标签是文案检索的关键词提示，**不是材质判断依据**
2. 正确逻辑应是：**先判品类 → 再在该品类的材质清单里选材质**
   例：图片识别为床垫 → 该床垫的内填充可能是乳胶 / 分区海绵 / 独袋弹簧（**新增维度：标签-材质**）

**新增数据文件 `materials.js`**
- `KB_MATERIALS`：品类 → { desc, items[] }，10 品类共 **103 个材质**
- 每个品类有 desc（如床垫=「内填充与结构材料」、茶几=「台面与框架材料」），UI 上直接用作字段标题
- `KB_TAG_ROLE`：常量的角色说明文案，侧栏和面板都引用它，避免误解
- **必须与 KB_CATEGORIES 品类对齐**，否则匹配无从判断

**匹配逻辑重写**
- `MATCH_PROMPT` 改为两段式明确指令：第一步判品类，第二步材质**必须从该品类清单里选，不能跨品类不能自创**
- 输出结构从 `matchedIds` 改为 `category + materials[]`
- **双重白名单校验**：prompt 里约束 + 前端 `sanitize` 再过滤一次。材质不在该品类清单内一律丢弃（模型不可全信）
- 素材不足时返回空数组，不硬凑——宁缺毋滥
- 入库识别的 `SYSTEM_PROMPT` 同步改用同一套材质库，两边标准一致；材质改成下拉选择并随品类联动

**筛选维度扩展**
- `state` 新增 `material` 字段，**精确匹配** material 字段（不用全文搜索，否则「岩板」会把文案里提到岩板对比的「实木」也带出来）
- 品类 / 材质 / 标签 / 关键词四者**可共存叠加**，语义为交集
- 原来「搜索与标签互斥」的设计已改为可叠加——材质定位需要「某品类 + 某材质」同时生效

**匹配结果界面重构**
- 结构：品类 → 匹配到的材质（可点）→ 特性标签·文案检索关键词 → 判断依据
- **每个材质标注「已入库/未入库」**：未入库的用虚线框标记
- 点已入库材质 → 直接筛选；点未入库材质 → 确认后跳「AI 识别入库」并预填品类+材质
- `switchToSave()` 造一份最小 result 复用 `renderResult`，避免依赖已清空的 DOM

**数据质量修复**
- 藤编/多层实木 各有一个重复标签，已去重
- **19 条内置条目的材质名不在新清单里**（如「乳胶」vs「天然乳胶」、「真皮」vs「头层牛皮」）→ 已把这些名字补进对应品类清单，保持原资料不动
- 最终校验：0 重复标签、0 材质缺失

**实测**：床垫复合结构 → 弹簧+乳胶复合/独袋弹簧/分区海绵（全部落在床垫清单内）；沙发 → 头层牛皮/高回弹海绵；非家具内容 → 品类「未识别」+ 合理引导。线上验证通过。

## 第六阶段：改版为「家具产品标签库」（2026-10-14）

**用户反馈**：拿到真实表格《家具产品标签库.xlsx》，要求按截图批注重构整个版面，标签体系换成表格里的。

**诊断出原版式的根本错误**：层级混乱——把「乳胶/岩板」这类**材质**当成了一级标签，而「床垫」才是品类。材质属于品类之下，特性标签属于文案检索关键词，三者不是同一层。

**数据源分析（重要发现）**
- 表格 4 个 sheet：`标签字典`(67行)、`产品卖点源`(19946行)、`产品标签库`(5行模板)、`标签治理`(空)
- **`抓取卖点原文` 列 19940 行全为空**，真正有内容的是 `SKU名称`（如「【白蜡木】加宽加厚无结松木排骨架，1500mm*2000mm，单床」）→ 从 SKU 名称提取卖点
- `标签字典` = 8 分类 / 66 维度 / 979 标签值，完全替换原自建的 4 维 41 标签

**构建流程（build/ 目录，不发布）**
- `build_tags.py` 主脚本 + `tag_rules.py` 814 条正则规则，输出到 `material-kb/tags-data.js` + `entries-data.js`
- 从 SKU 描述自动打标：每维度最多 3 个标签，平均 2.6 个/条，覆盖 130/979 标签值
- 产出 1830 条条目（13 大类，每类上限 200），文件 628KB
- **规则不能写在主脚本里**：814 条正则内联会让 Python 解析器栈溢出（Parser stack overflowed），必须独立成文件
- **元组结构陷阱**：`(cat, dim, [r'正则', '标签值'])` 会被解包成 `pats=正则字符串, val=标签值`，导致 `re.search(标签值, text)` 几乎命中一切，单条标签从 2.5 个膨胀到 207 个。正确写法 `([正则], 标签值)`

**版面重构（对应截图 8 处批注）**
1. 搜索改为真筛选（原来只是装饰），覆盖型号/材质/卖点/标签
2. 左栏层级：品类 → 材质（随品类联动）→ 特性标签（8分类/66维度手风琴）
3. 卡片标题改为**材质**（主）+ 品类（次），材质可点击筛选
4. 3-5 个关键词概括材质特性（`.kw`）
5. 规格三行独立成字段（规格尺寸/适用/注意），右侧留空可点填（contenteditable）
6. 材质支持**包含关系**：筛「弹簧」命中「独立袋装弹簧」（双向 indexOf）
7. 每张卡片加「复制描述」按钮
8. 移除噪音标签（自动识别的适用人群等改为独立可编辑字段）

**AI 识别适配新体系**
- prompt 重写：品类 → 材质 → 标签，标签按「分类/维度」分组
- 前端二次白名单校验：`legalIndex()` 逐维度过滤，非法标签丢弃
- 标签存 JSON 字符串而非扁平数组（结构化后可按维度筛选）
- **踩坑：一次性给 979 个标签值，模型偷懒只填少数字段，tags 全空**
  - 试过两阶段（先选维度再选值），模型不返回 `dims` 字段，更复杂反而更糟
  - 最终方案：**单阶段 + 明确格式示例** + 每个维度的可选值分组列出，验证输出 4 个标签成功
- 「密度规格」改为「规格/尺寸」——AI 常把 1800mm×2000mm 填进密度字段，语义不符

**环境限制**：本机到 cdn.jsdelivr.net 的网络被阻断（curl exit 35、浏览器 ERR_CONNECTION_RESET），SDK 加载不稳定。线上环境正常，但测试时需 `waitForFunction` 等 90 秒并做好重试。

**验证**：线上实测搜索（乳胶34/岩板49）、品类材质联动、标签维度筛选、规格就地编辑、复制、AI 识别入库全链路通过，无 JS 错误。

## 第十阶段：AI 识别入库支持文档（2026-10-15）

**用户需求**：AI 识别入库要能读文档内容并自动匹配入库；一份文档含多个产品时**拆成多条，一款一条**。

**确认过的需求（AskUserQuestion）**
- 文档类型：Word / TXT / Excel
- 入库粒度：拆成多条，一款一条

**文档解析：零外部依赖**
- 新增 `material-kb/doc-parse.js`
- **关键决策**：本机到 cdn.jsdelivr.net 的网络被阻断（curl exit 35），不能用 mammoth/xlsx 这类 CDN 库
- 解法：**docx 与 xlsx 本质都是 zip**，用浏览器原生 `DecompressionStream('deflate-raw')` 解压，
  手工解析 zip 中央目录 + local file header，再读 `word/document.xml` / `xl/worksheets/*.xml`
- **zip 陷阱**：local header 的 extra 长度可能与 central directory 不同，必须重新读 `lNameLen/lExtraLen`，否则数据偏移错位
- 支持：docx（段落 + 表格行）、xlsx（sharedStrings + 单元格引用，处理 inlineStr/共享串/空列裁剪）、txt/md/csv/tsv
- 统一返回 `[{type:'p'|'row', text, cols}]`

**批量识别**
- `ingest.js` 新增 `matchDocument(blocks, onProgress)`：`chunkBlocks()` 按 2200 字切块 → 逐块调 LLM → 合并 products
- 单块失败不中断整体（catch 后继续下一块）
- `panel.js` 新增 `renderBatch()` / `saveBatch()`：勾选式批量入库，支持全选/全不选、逐条进度、单条失败不影响其他

**模型输出的归一化（关键）**
实测模型返回有三处不合规，都在 `sanitizeProduct` 里做了兼容：
1. **`tags` 的键写成自定义分组名**（材质/特点/场景）而非「分类/维度」
   → `normTags()`：按标签值反查真实归属 `tagValueKeys()`，键不合法时归到正确的分类下
2. **`materials` 返回字符串**「白蜡木、松木」而非数组
   → `normMaterials()`：字符串按分隔符切；再「去修饰词」匹配（「白蜡木实木框架」→「白蜡木」），**取最长匹配**避免「实木」吃掉「多层实木」
3. **`category` 自造值**「儿童床」库里没有
   → `normCategory()`：加别名表 + 双向包含匹配，**取最长匹配**避免「软包床」被「床」吃掉

**数据库踩坑（重要）**
- 表 `material_notes` 的真实列：`id, owner_id, owner_name, category, material, source_text, image_path, image_url, feel, tags, copy_items, fit, caution, confidence, raw_text, created_at`
- **`tags` / `copy_items` 是数组列**，传 `JSON.stringify` 会报 `malformed array literal`
- **没有 spec/title/materials/keywords 等列**，传了报 `Could not find the 'xxx' column in the schema cache`
- `select *` 在空表时返回空数组，拿不到列名 → 只能**逐列试探**：捕获错误里的列名 → 剔除该列 → 重试
- 最终方案：固定字段严格按真实列写，多材质/关键词/标签维度/规格尺寸全塞进 `raw_text`（JSON），读取时还原
- **教训**：一开始靠猜字段名（spec/keywords/...），连续失败 4 次；必须先 insert 一条最小记录，**用返回对象的 key 反查真实列**

**类名冲突**
批量结果的 `<label class="ai-pick">` 与上传按钮 `.ai-pick` 撞名，导致测试脚本误选。产品项改为 `.ai-item` / `.ai-itemmain`。

**验证**：5 产品 docx → 识别拆分 5 条全对（品类/材质/标签/关键词均正确）→ 入库成功 → 卡片正常渲染 → 「只看我添加的」筛选命中 7 条，无 JS 错误。

**关键 API 形状**（读源码 + 实测得到，文档没写清）
- `signUp` 需要 `verificationToken`，**不能只传账号密码注册**
- `signInWithOtp({ email })` 内部会自己发验证码，并返回一个**可调用对象**：
  ```js
  const d = await auth.signInWithOtp({ email })
  // d = { verificationId, isExistingUser, verify }
  await d.verify({ token, password })   // → verifyOtp → 自动完成登录
  ```
  → 所以正确用法是两步：`startSignIn(email)` 拿 pending → `finishSignIn(pending,...)` 验码登录
- **参数名坑**：`sendOtp` / `signInWithOtp` 用 `{ email }`，不是 `{ username }`。
  传 username 会报 `requires exactly one of email or phone`

## 第十五阶段：突破 20MB 文件限制（2026-07-18 下午）

**用户反馈**：上传文件报「文件超过 20MB，请拆分后再试」。

**根因**：`doc-parse.js` 里写死 `MAX_BYTES = 20MB`，
而且 `readZip()` 会把 **zip 内所有条目都 slice 进内存**——包括图片。
所以限制不只是数字问题，是**架构问题**：文档再大，我们只用到那几个 XML。

**解法：只读需要的条目，其余全部跳过**
- `readZip(buf, only)` 增加 `only` 正则参数，不匹配的直接 `continue`（连 slice 都不做）
- docx：`/^word\/document\.xml$/` → 跳过 `word/media/*`（图片，占 99% 体积）
- xlsx：`/^(xl\/worksheets\/sheet\d+\.xml|xl\/sharedStrings\.xml|xl\/workbook\.xml)$/` → 跳过图片与样式表
- 记录 `files._skipped` 便于排查

**限制重新设计**
- `MAX_BYTES = 200MB`（原始文件上限）
- `MAX_TEXT = 12MB`（**提取出的文字**上限，约 600 万字）
  → `capBlocks()` 截断并在末尾追加「已读取前 N 段，共 M 段」提示
- 真正的瓶颈是文字量，不是文件体积

**顺带修了 XML 解析的脆弱性**
测试中 `big.docx` 报 `XML 解析失败：a:blip prefix is unbound`——
第三方工具/图片格式产生的**未声明命名空间前缀**会让 `DOMParser` 整份失败，
结果「明明有文字却读不出来」。

改为 **正则提取**，不依赖 DOM：
- `stripXml()`：去标签 + 解实体（含 `&#123;` 与 `&#x1F;` 两种数字实体）
- 段落 `<w:p>`、表格行 `<w:tr>` 用正则匹配，单元格 `<w:tc>` 拆列
- 对命名空间前缀天然免疫
- 旧的 DOMParser 路径改名 `parseDocxOld` 并**删除**（`check.js` 帮了大忙）

**`check.js` 再次立功**
删 `parseDocxOld` 时误删了 `colToNum`（列引用 A→0、AA→26 的转换函数），
`node check.js` 立刻报出 → 补回。
这已是它第三次在提交前拦住问题。

**验证**
```
① 23.5MB / 300 张图片的 docx
   → 2.3 秒解析完成，240 段全读出，预览正常 ✅
② 普通含表格 docx
   → 段落 4 段 + 表格行 2 行，格式正确 ✅
```

**注意**：xlsx 仍走 DOMParser（表格结构规范、命名空间声明完整），未改。
如果线上遇到 xlsx 解析失败，同样需要改成正则方案。

## 第十六阶段：重写 xlsx 解析（2026-07-18 晚）

**用户反馈**：Excel (.xlsx) 选完文件立即报「解析失败」，选完即报错（不是识别阶段）。

**发现并修复的问题**
1. **`workbook.xml.rels` 被自己的过滤正则排除**

- 单元格类型分流：
  - `t="s"` → `<v>` 是 sharedStrings 下标
  - `t="inlineStr"` → 直接取内部文本
  - 其他（数字/日期）→ 取 `<v>` 原值
- `decodeXml()`：解码 `&lt; &gt; &quot; &apos; &amp; &#123; &#x1F;`（十进制+十六进制）

- 多工作表按文件名序号读取
- 删掉不再使用的 `parseXml` / `textOf`（DOMParser 依赖全部清掉）

## 第十七阶段：修复 157MB 超大 Excel 识别（2026-07-18 晚）

**用户文件**：`桌面/全店在售品及卖点文案汇总（截止7月31日）.xlsx`（157MB）

**诊断出三个原因**
1. **解压后体积爆炸**：文件 157MB，但 `xl/worksheets/sheet1.xml` 解压后 **861MB**。
   表格共 19945 行 × 9 列，其中「产品卖点文案」列极长（含图片清单/OCR文本）。
   原实现一次性解压进内存 → 浏览器直接崩。
2. **行切分方式错误**：原正则 `<row[^>]*>.*?</row>` 依赖闭合标签。
   实测 900KB 里只匹配到 **1 行**——因为最后一行未闭合时，
   正则会一路向后吞掉几十 MB 直到找到下一个 `</row>`。
   改为**按 `<row` 开标签切分**（`split(/(?=<row\b)/)`），不依赖闭合。
3. **调用次数爆炸**：`chunkBlocks` 按 2200 字符切块 → 逐块调模型。
   1500 行会是 1500 次调用，时间与费用都不可接受。

**改造**
- 新增 `streamEntry(f, onChunk)`：**流式解压**
  - `DecompressionStream` + `getReader()` 逐块读，累加到 4MB 才交给上层
  - `onChunk` 返回 `false` 即 `stopped=true`，**剩余数据不再解压** → 内存可控
- `MAX_ROWS = 1500`：读到上限就中止，并在末尾追加提示
  「（表格共约 N 行，本次已读取前 1500 行。其余部分可拆分后再上传。）」
- `MAX_BYTES` 200MB → **400MB**
- `chunkBlocks` 表格分支：**每次 12 行一批**，且每批**重复表头**，让模型知道列含义
- BATCH_PROMPT 增加第 0 条：按 `|` 分隔的列理解表头，**忽略 ID/链接/编码/日期等无关列**
- 单元格正则补全终止条件：`</c>|(?=<c)|(?=<row)|$`（兼容行内最后一个未闭合单元格）

**该文件的列结构**
```
A B店商品ID | B 商品链接 | C 主型号 | D 子型号 | E 淘宝类目 | F SKU名称 | G 商家编码 | H 详情图数 | I 产品卖点文案
```
识别真正需要的是 **E（类目）+ F（SKU名称）+ I（卖点文案）**，
A/B/G/H 是噪音列，提示词已让模型忽略。

**验证**

```

## 第十八阶段：自动分批续跑（2026-07-18 晚）

**用户需求**：文档有近 2 万行，一次只能读 1500 行，要能自动接着处理下一批。

**实现**
1. `matchDocument(blocks, onProgress, opts)` 扩展：

3. `init()` 加载 SDK 增加**自动重试 3 次**（每轮 20 秒），

1. **续跑丢失已识别结果**：`collected` 原本是 `runDocument()` 的局部数组，

## 第十九阶段：绕开浏览器，直接批量入库（2026-07-18 傍晚）

**用户反馈**：前端上传仍然失败（同一提醒），授权「你直接帮我入库吧」。

**决策**：写 Node 脚本 `ingest-run.js`，在本地读 xlsx → 云端 LLM 识别 → 直接写库。
好处：不受浏览器内存/CDN 波动影响，可断点续跑，出错可控。

**关键技术：157MB xlsx 的本地流式解析**
```js
// 1) 从尾部找 EOCD（0x06054b50）
// 2) 读中央目录定位 xl/worksheets/sheet1.xml 的 localOffset
// 3) 分块读 4MB → zlib.createInflateRaw() 流式解压
// 4) 累积到 4MB 就切行，够到行数上限立即 destroy + 关闭 fd
```
**踩坑**：`eocd` 是 tailBuf 内的**相对位置**，而 `cdOff` 是**绝对偏移**，
两者相减得到负数 → 必须换算 `eocdAbs = size - tailLen + eocd`。
之前报「中央目录异常」就是这个原因。

**批次策略**：每批 8 行，提示词里带**完整标签维度清单**（1473 个维度），
要求模型输出的 tag 键必须是「分类/维度」原文。

**JSON 容错**（模型偶发返回 ```json 包裹或流式截断）：
剥 markdown 围栏 → 尝试 parse → 失败则补齐未闭合的引号/括号再 parse。

**去重规则**：同一产品不同尺寸（1200/1350/1500mm）只出一条，
避免 SKU 尺寸变体重复入库。在提示词第 6 条明确要求。

**断点续跑**：`node ingest-run.js <行数> <起始行>`，如 `ingest-run.js 800 200`。

**第一批结果（200 行 → 191 条）**
```
